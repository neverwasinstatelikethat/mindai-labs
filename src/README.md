## Общая архитектура

Серверная часть построена по принципу **LLM-управляемого GraphRAG**: LLM планирует обработку, выбирает инструменты и формирует выводы по графовому контексту; доменная логика, маршруты рассуждения и ответы не кодируются жёсткими правилами.

```
Запрос → Классификация намерения → План запроса → Выбор инструментов
    → Исполнение (поиск + граф + аналитика) → Контроллер (достаточно ли данных?)
    → Рассуждение → Критик → [Улучшение] → Завершение → Ответ
```

Все LLM-вызовы используют **структурированный вывод**: каждый агент возвращает Pydantic-модель, валидируемую по JSON Schema.

#### Проверка прав доступа

Каждый запрос проходит через middleware `access_middleware`: cookie `nk_session` резолвится в учётную запись (`services/accounts.py`), из неё строится `Principal`, всё под `/api/v1/` без действующей сессии получает `401`, а state-changing запрос с cookie проверяется на доверенный источник (`TRUSTED_ORIGINS`). Эндпоинты, требующие специальных разрешений, используют зависимость `require_permission()`; набор прав задают `BASE_POLICY` и `EXPERT_POLICY` в `services/governance.py`.

#### Фильтрация данных

При выполнении запроса применяется двойная фильтрация:
1. **До поиска** — набор доступных классов данных передаётся в рабочий процесс.
2. **После поиска** — результаты дополнительно фильтруются: утверждения с неподходящим статусом удаляются вместе со связанными конфликтами, пробелами и узлами графа.

### `agents/` — Рабочий процесс агентов

#### `workflow.py` (543 строки)

Реализует конечный автомат на LangGraph `StateGraph`. Состояние `ResearchState` передаётся между узлами, каждый узел — отдель LLM-агент.

**Узлы рабочего процесса:**

| Узел | Агент | Назначение |
|---|---|---|
| `planning_agent` | Планирование | Классифицирует намерение запроса, формирует `QueryPlan` и начальный `AgentActionPlan` одним вызовом LLM |
| `tool_executor` | Исполнение инструментов | Выполняет выбранные инструменты (поиск, обход графа, анализ конфликтов и т.д.) |
| `controller` | Контроллер | Оценивает, достаточно ли собранных данных; решает, продолжить сбор или перейти к синтезу |
| `action_planner` | Перепланирование | Уточняет план инструментов с учётом уже собранных данных и обнаруженных пробелов |
| `reasoner` | Рассуждение | Синтезирует структурированный ответ из собранных находок и доказательств |
| `critic` | Критик | Проверяет соответствие вопросу, цитирования, числовую точность; одобряет или возвращает на доработку |
| `improver` | Улучшение | Исправляет ответ по замечаниям критика (не более `AGENT_MAX_REVISIONS` ревизий) |
| `finalize` | Завершение | Формирует финальный `AnswerPayload` с рассчитанной уверенностью |

**Маршруты:**
- `controller` → `action_planner` (нужны ещё данные) или `reasoner` (данных достаточно)
- `critic` → `improver` (не одобрено и лимит ревизий не исчерпан) или `finalize` (одобрено)
- Контроллер принудительно переключается на `reason`, когда раунды инструментов исчерпаны.

**Бюджет запроса** задаётся конфигурацией (`AGENT_DEADLINE_SECONDS`, `AGENT_MAX_TOOL_ROUNDS`, `AGENT_MAX_REVISIONS`, `CONTEXT_TOKEN_BUDGET`; см. `config.py`). При упоре в дедлайн, предел шагов или ошибку узла `run()` и `stream()` возвращают частичный ответ: собранные находки сохранены, причина — в `degradation_reasons`, уверенность понижена. Молчаливой обрезки нет. Недоступную модель это не маскирует: `ModelUnavailableError` не подменяется частичным ответом и уходит в `503`.

**Инструментация:** каждый узел обёрнут в `_instrument()`, который замеряет время выполнения и фиксирует метрики (успех/отказ) в `AgentMetricsRegistry`.

### `services/` — Бизнес-логика

#### `knowledge.py` (737 строк)

**Назначение:** хранение и поиск по базе знаний. Реализует протокол `KnowledgeBase` с двумя адаптерами.

**`InMemoryKnowledgeBase`** — адаптер для тестов и локального запуска:
- Хранит документы, утверждения и граф в памяти
- Предзаполняет(seed) типовые данные по водоподготовке (5 утверждений, 9 узлов графа, 3 сообщества)
- **Ранжирование:** два режима — лексический (базовый) и гибридный (лексический + семантический по цитатам + графовый по источнику и субъекту)
- **Числовые фильтры:** применение ограничений к нормализованным значениям наблюдений
- **Версионирование:** метод `supersede_finding()` создаёт новую версию утверждения и связывает через SUPERSEDES
- **История версий:** метод `claim_history()` возвращает всю цепочку версий утверждения
- **Фильтрация по классу данных:** pre-retrieval ACL на уровне поиска

#### `provider.py`

**Назначение:** единственный LLM-провайдер платформы (GigaChat) со структурированным выводом.

| Провайдер | Описание |
|---|---|
| `GigaChatProvider` | GigaChat (Сбер), `mode = "gigachat"`. Асинхронные вызовы через SDK; клиент и токен переиспользуются, одновременность ограничена `GIGACHAT_MAX_CONCURRENT` |
| `UnavailableProvider` | `GIGACHAT_API_KEY` не задан: `mode = "unavailable"`, каждый LLM-вызов → `ModelUnavailableError` (`503` в API) |

**Фабрика `build_provider()`:** возвращает `GigaChatProvider` при наличии ключа и `UnavailableProvider` без него. Резервной модели и автоматического переключения по ошибке провайдера в контуре нет — ответ либо собирается на GigaChat, либо честно помечается недоступным.

**Повторы:** транспортную задержку гасит одна retry-политика SDK (`GIGACHAT_MAX_RETRIES`), поверх неё — не больше двух попыток schema-repair (`_SCHEMA_REPAIR_ATTEMPTS`). Живой GigaChat портит structured output и после правки (то верхние ключи, то обрыв JSON при `finish=stop`), а подсказка при повторе теперь называет поле с путём, иначе правка расходилась. Бюджет вывода задаёт `GIGACHAT_MAX_OUTPUT_TOKENS`: без него JSON режется дефолтом провайдера. Токен запрашивается до первого обращения, поэтому ошибка ключа видна как `ModelUnavailableError`, а не как `500` на первом узле.

**Структурированный вывод:** каждый вызов `complete_model(system, user, schema)` формирует системный промпт с JSON Schema целевой модели и парсит JSON-ответ LLM в Pydantic-экземпляр. При невалидном JSON выполняется один повторный запрос с исправлением; после исчерпания попытки — `ModelUnavailableError`.

#### `ingestion.py` (101 строка)

**Назначение:** импорт документов в базу знаний.

**Процесс импорта:**
1. LLM извлекает сущности и утверждения из текста документа (`IngestionBundle`)
2. Применяется сопоставление сущностей: синонимы и переводы сводятся к каноническим именам
3. Валидация по онтологии (SHACL-ограничения)
4. При ошибке валидации — автоматический повторный вызов LLM с описанием нарушения
5. Запись в базу знаний (граф + утверждения)
6. Регистрация предложений слияния сущностей

#### `document_parser.py` (151 строка)

**Назначение:** разбор загруженных файлов в единый формат `DocumentRequest` с фрагментами.

| Формат | Парсер | Особенности |
|---|---|---|
| **PDF** | `fitz` + `pytesseract` | Постраничное извлечение текста; при отсутствии текста — OCR (русский + английский) |
| **DOCX** | `python-docx` | Абзацы группируются блоками до 8000 символов; таблицы разбираются построчно |
| **XLSX** | `openpyxl` | Каждая строка листа — отдельный фрагмент с указанием листа и диапазона ячеек |
| **JSON** | Стандартная библиотека | Один фрагмент на весь документ |
| **TXT** | Стандартная библиотека | Один фрагмент, UTF-8 |

Ограничение размера файла — 20 МБ.

#### `research_intelligence.py` (114 строк)

**Назначение:** обнаружение конфликтов и пробелов в знаниях.

- **Обнаружение конфликтов:** для каждой пары утверждений с одинаковыми субъектом, предикатом и свойством проверяется совместимость областей применения и непересечение нормализованных числовых диапазонов.
- **Обнаружение пробелов:** строится полное декартово произведение измерений research space и вычитаются покрытые комбинации; непокрытые — пробелы.
- **Комплексный анализ:** метод `analyze()` возвращает `IntelligenceReport` с конфликтами, пробелами и количеством проанализированных утверждений.

#### `evolution.py` (74 строки)

**Назначение:** самообучение через экспертную обратную связь.

**Процесс:**
1. Эксперт оставляет обратную связь (`FeedbackRequest`: принять / отклонить / исправить)
2. LLM генерирует `EvolutionDraft` — предложение по улучшению (промпт, правило, псевдоним, эталонный случай)
3. Создаётся `EvolutionProposal` со статусом `proposed`
4. Запускается A/B-эксперимент: базовый рабочий процесс против кандидата с новой политикой
5. Если кандидат не хуже базового по всем метрикам — решение `promote`
6. После успешного эксперимента предложение проходит ручную проверку (`proposal:review`)
7. Принятое предложение встраивается в промпты рабочего процесса (`active_policy()`)

#### `governance.py` (48 строк)

**Назначение:** контроль доступа и журнал аудита.

- **`AccessPolicyEngine`** — принимает решение о доступе к ресурсу на основе разрешений субъекта, класса данных и области проекта.
- **`InMemoryAuditLog`** — журнал событий аудита в памяти. Возвращает глубокие копии событий (защита от подмены) и поддерживает фильтрацию по `correlation_id`.

#### `comparison.py` (97 строк)

**Назначение:** сравнительный анализ сущностей по числовым свойствам. Строит матрицу, где строки — сущности (субъекты утверждений), столбцы — свойства (из наблюдений). Каждая ячейка содержит значение, единицу, цитату-доказательство и уверенность.

#### `exporter.py` (211 строк)

**Назначение:** экспорт ответа в три формата:
- **Markdown** — структурированный текст с разделами (утверждения, конфликты, пробелы, рекомендации, метаданные)
- **JSON-LD** — связанные данные с контекстом schema.org и собственной онтологией
- **PDF** — генерация через PyMuPDF с автоматическим разбиением на страницы A4

#### `embeddings.py`

**Назначение:** векторные эмбеддинги для семантического поиска — GigaChat `/embeddings` (модель `GIGACHAT_EMBEDDINGS_MODEL`). Один клиент переиспользует токен и соединение, индексация корпуса идёт батчами до 8 текстов, текст ограничивается 8000 символов. Размерность задаётся `EMBEDDING_DIMENSIONS` (по умолчанию 1024) и приводится к фактической из ответа модели, по ней строится маппинг индекса Elasticsearch. Векторная ветка опциональна: без ключа или при ошибке провайдера (`EmbeddingError`) гибрид остаётся лексико-графовым.

#### `resolution.py`

**Назначение:** верстак сопоставления сущностей. Хранит предложения слияния (link/create), поддерживает проверку (accept/reject/revert). Каждое предложение содержит упоминание, каноническое имя, уверенность и обоснование.

#### `infrastructure.py`

**Назначение:** фабрика базы знаний. В зависимости от `knowledge_backend` создаёт либо `InMemoryKnowledgeBase` (тесты и локальный запуск), либо адаптеры Neo4j + Elasticsearch (рабочий контур аналитиков).

#### `ontology.py`

**Назначение:** SHACL-валидация извлечённых данных. Проверяет, что типы сущностей, предикаты и структура утверждений соответствуют доменной онтологии (`ontology/shapes.ttl`).

#### `preload.py`

**Назначение:** предзагрузка корпуса документов из локальной файловой системы. Сканирует директорию `SOURCE_ROOT`, разбирает каждый файл и передаёт в конвейер импорта. Поддерживает три режима: `full` (полный цикл с LLM-извлечением), `structural` (только структура), `semantic` (структура + семантическое извлечение).

#### `agent_metrics.py`

**Назначение:** реестр метрик агентов. Для каждого агента фиксирует количество вызовов, успешных/неуспешных, процент успеха, среднюю и перцентильную (p50, p95) латентность.

#### `corpus.py`

**Назначение:** управление корпусом документов. Обнаружение файлов, фильтрация по размеру и формату, формирование отчётов предзагрузки.

#### `graph_rebuilder.py`

**Назначение:** перестройка графа знаний из сохранённых данных. Используется при миграциях или восстановлении после сбоев.

### `evaluation/` — Оценочный контур

**Файл:** `harness.py` (246 строк)

**Назначение:** измеримая оценка качества ответов и поиска.

#### Метрики ответа

| Метрика | Как считается |
|---|---|
| `citation_coverage` | Доля находок с хотя бы одним доказательством |
| `numeric_support` | Доля числовых утверждений с доказательствами |
| `unsupported_claim_ratio` | Доля находок, чьи числа не встречаются в цитате доказательств |
| `mean_finding_confidence` | Средняя уверенность находок |
| `overall` | Среднее `citation_coverage`, `numeric_support` и `1 - unsupported_claim_ratio` |

Прогон считается пройденным, если `citation_coverage` и `numeric_support` не ниже `PASS_TOLERANCE` (0.999), `unsupported_claim_ratio` не выше `1 - PASS_TOLERANCE` и `overall >= 0.8`.

#### Бенчмарк поиска (`benchmark_retrieval`)

Сравнивает гибридный и лексический режимы ранжирования на эталонных случаях из `preload_manifest.json`. Считает recall@3, precision@3, MRR, NDCG@3 для обоих режимов. Проверяет «утечку» (заголовок источника не должен копироваться в текст запроса).

#### Сквозной бенчмарк (`benchmark_pipeline`)

Запускает рабочий процесс на эталонных вопросах, замеряет recall источников, покрытие цитирования, процент пройденных случаев и среднюю латентность. Сравнивает с лексическим базовым подходом.

#### Поддержка A/B-экспериментов

Метод `evaluate_workflow()` принимает любой рабочий процесс (в том числе с внедрённой политикой) и набор эталонных случаев. Возвращает агрегированные метрики и детальные результаты по каждому случаю.

## Поток данных

### Импорт документа

```
Файл → document_parser (PDF/DOCX/XLSX/JSON/TXT)
    → DocumentRequest с фрагментами
    → ingestion.ingest()
        → LLM: извлечение сущностей и утверждений
        → Сопоставление сущностей (синонимы → канонические имена)
        → SHACL-валидация (при ошибке — повторный LLM-вызов)
        → knowledge.ingest() (запись в граф + утверждения)
    → DocumentReceipt (идентификатор, контрольная сумма, количество утверждений)
```

### Исследовательский запрос

```
QueryRequest (вопрос, язык, режим)
    → planning_agent (намерение + план запроса + выбор инструментов)
    → tool_executor (поиск + граф + аналитика)
    → controller (достаточно данных? → да/нет)
        → нет → action_planner → tool_executor (повтор, до `AGENT_MAX_TOOL_ROUNDS` раундов)
        → да → reasoner (синтез ответа)
    → critic (проверка качества)
        → не одобрено → improver → critic (до `AGENT_MAX_REVISIONS` ревизий)
        → одобрено → finalize → AnswerPayload
    → Пост-обработка: ACL-фильтрация + оценка → QueryResponse
```

### Экспертная обратная связь

```
FeedbackRequest (вердикт, комментарий, исправление)
    → evolution.propose() → LLM генерирует EvolutionDraft → EvolutionProposal
    → (опционально) experiment: baseline vs candidate workflow → EvolutionExperiment
    → review: accept/reject → если accepted → пересоздание workflow с новой политикой
    → (опционально) supersede_finding: создание новой версии утверждения
```

## Ключевые технические решения

1. **LLM-управляемый рабочий процесс** — все решения о маршрутизации, выборе инструментов и синтезе ответа принимает LLM; код только ограничивает пространство действий (безопасный action space).

2. **Структурированный вывод** — каждый LLM-вызов возвращает валидированную Pydantic-модель; JSON Schema передаётся в системном промпте.

3. **Полноконтекстное извлечение** — документы не разбиваются на мелкие фрагменты перед LLM; весь текст подаётся как единый контекст (с обрезкой при превышении лимита токенов).

4. **Двойная ACL-фильтрация** — ограничения применяются и до поиска (на уровне рабочего процесса), и после (на уровне API-ответа).

5. **Идемпотентный импорт** — контрольная сумма SHA-256 предотвращает дублирование; повторная обработка документа не создаёт записей.

6. **Версионирование утверждений** — экспертная корректировка создаёт новую версию с привязкой SUPERSEDES; исходная версия сохраняется в истории.

7. **Один провайдер и явная деградация** — GigaChat без резервной модели: недоступная модель отдаёт `503`, а исчерпанный бюджет запроса — частичный ответ с `degradation_reasons`. Ни то, ни другое не маскируется под полный результат.
